# /github-create-pr — Open a PR for Newly-Completed Work

> **Purpose**: Detect newly-completed subtasks in `docs/tasks.md` (those with `[x]`, `Impl:`, and either no `PR:` field or a stale one), group them by parent task, and open one Pull Request per completed task. Each PR summarizes the work, links the corresponding issues with `Closes #N` keywords for auto-closure on merge, and posts a comment on each linked issue with a back-reference to the PR. The skill operates strictly on the current branch — it never switches branches or auto-creates them. **Pull requests are never merged automatically — every PR requires human review before being merged into the default branch.**
> **Prerequisites**:
>   - `docs/tasks.md` must exist (generated by `/design`)
>   - `gh` (GitHub CLI) must be installed and authenticated
>   - The current directory must be a git repository connected to a GitHub remote
>   - The current branch must NOT be the repository's default branch
> **Output**: One GitHub PR per completed task + updated `docs/tasks.md` with `PR:` references inline + comments on linked issues
> **Iterative**: Yes — designed to be re-run safely. Existing PRs are updated when more subtasks under the same task are completed; new PRs are only created when there is genuinely new work to publish.
> **Position in workflow**: Run after `/implement` checks off subtasks. Can also be invoked manually any time newly-completed work needs to be PR'd.

---

## Why This Skill Exists

`/implement` checks off subtasks in `docs/tasks.md` and adds implementation file references, but it does NOT open PRs. This skill closes that loop: write code → tests pass → tasks.md updates → run this skill → PR opens → reviewer approves → merge → GitHub auto-closes the linked issues.

The result is a tight feedback loop where every meaningful chunk of completed work flows from local source of truth (`docs/tasks.md`) to remote tracking (GitHub Issues + PRs) without manual issue triaging — but with mandatory human review before any code lands on the default branch.

If GitHub issues for the relevant tasks don't yet exist (no `GitHub:` references in `docs/tasks.md`), this skill will invoke `/github-init` first to create them, then proceed with PR creation. You don't need to run `/github-init` separately.

---

## Instructions for the Agent

You are creating GitHub PRs for newly-completed implementation work. Read `docs/tasks.md`, `docs/architecture.md`, `docs/design.md`, and `docs/integration-registry.md` (if it exists) before starting.

**Behavior rules:**
1. **Verify environment first**: Confirm `gh` CLI is installed and authenticated, and that the current directory is connected to a GitHub remote. If either check fails, stop and tell the developer how to fix it.
2. **Strict current-branch operation**: The skill operates ONLY on the branch the session is currently on. Never switches branches, never checks out a different branch.
3. **Refuse on default branch**: If the current branch is the repository's default branch (`main`/`master`), refuse and tell the developer to switch to a feature branch.
4. **No auto-merging**: The skill NEVER merges PRs. PRs are opened in DRAFT or REGULAR state and require human review before merge. The skill posts comments and labels but never approves, never merges, never enables auto-merge.
5. **Detect newly-completed subtasks**: A subtask is "newly completed" when it has `[x]`, a non-pending `Impl:` field, AND either no `PR:` field OR a `PR:` field that points to a closed-without-merge PR. (Closed-but-merged PRs mean the work is shipped — no new PR needed.)
6. **One PR per parent task**: Group newly-completed subtasks by their parent task. For each parent task with at least one newly-completed subtask, open or update one PR.
7. **Auto-create issues if missing**: If a newly-completed subtask has no `GitHub:` field (the issue doesn't exist yet), invoke the issue-creation logic from `/github-init` to create it before opening the PR. The skill is standalone — it doesn't require `/github-init` to have been run separately.
8. **Title format is non-negotiable**: PR titles must start with the task ID (e.g., `T1.1 — Login Flow`). If a single PR covers multiple tasks (work spread across the same branch), use the format `T1.1, T1.2 — Login Flow & Session Management`.
9. **Body structure is non-negotiable**: Every PR body must contain the eight required sections (Summary, Subtasks Completed, Parent Task, Test Plan, Configuration Instructions, Files Changed, Linked Issues, Footer). See "PR Body Template" below.
10. **Auto-close issues via PR keywords**: PR bodies use `Closes #N` keywords for every linked issue. GitHub auto-closes them when the PR merges.
11. **Comment on every linked issue**: After opening or updating the PR, post a comment on each linked issue with a back-reference for visibility before merge.
12. **Write back to `docs/tasks.md`**: After the PR is opened, add a `PR:` field to the parent task and to each subtask included in the PR.

## Step 1 — Environment Verification

Run these checks in order. Stop on any failure.

1. **Check `gh` is installed**: Run `gh --version`. If not, instruct: "Install GitHub CLI from https://cli.github.com and re-run."
2. **Check `gh` is authenticated**: Run `gh auth status`. If not, instruct: "Run `gh auth login` and re-run."
3. **Check repo is connected to GitHub**: Run `gh repo view --json nameWithOwner`. If it fails, recommend running `/github-init` first to walk through remote setup.
4. **Check git state — current branch**:
   - Determine `DEFAULT_BRANCH` via `gh repo view --json defaultBranchRef -q .defaultBranchRef.name`
   - Determine `CURRENT_BRANCH` via `git branch --show-current`
   - If `CURRENT_BRANCH` is empty (detached HEAD) → stop, tell developer to checkout a named branch
   - If `CURRENT_BRANCH == DEFAULT_BRANCH` → REFUSE. Tell the developer:
     > "The current branch is `{DEFAULT_BRANCH}`, the repository's default branch. /github-create-pr will not commit or open PRs against the default branch.
     >
     > Switch to a feature branch (e.g., `git checkout -b agentic/T1.1-login-flow`) and re-run."

---

## Step 2 — Read & Validate `docs/tasks.md`

1. Read `docs/tasks.md`
2. Parse the hierarchy: extract every milestone, task, and subtask with their IDs, descriptions, statuses, `GitHub:` refs, and `PR:` refs
3. Validate the structure (same as `/github-init` Step 2). If validation fails, stop and recommend `/docs-sync`.

---

## Step 3 — Detect Newly-Completed Subtasks

For each subtask in `docs/tasks.md`, evaluate if it is **newly completed**:
- Subtask is marked `[x]`
- Subtask has a non-pending `Impl:` field (a real file path)
- Either: no `PR:` field, OR a `PR:` field that points to a CLOSED-WITHOUT-MERGE PR (verify via `gh pr view {n} --json state,mergedAt`)

Group these by parent task. The skill will open one PR per parent task that has at least one newly-completed subtask.

If no newly-completed subtasks exist, stop and tell the developer:
> "No newly-completed subtasks found in `docs/tasks.md`. Either nothing has been implemented yet, or all completed work is already linked to merged PRs. Nothing to do."

---

## Step 4 — Auto-Invoke `/github-init` for Missing Issues

For each newly-completed subtask AND its parent task AND its parent milestone, check if the corresponding GitHub item exists (i.e., has a `GitHub:` reference in `docs/tasks.md`).

If ANY of these are missing GitHub references:
1. Tell the developer: "[n] items in scope are not yet on GitHub. Invoking /github-init to create them before opening PRs."
2. Run the logic from `/github-init` Steps 3-6 (label setup, milestone sync, task issue sync, subtask sub-issue sync) — but ONLY for the items in scope (the parent milestones, parent tasks, and newly-completed subtasks under them). Do NOT do a full sweep — that's `/github-sync`'s job.
3. Capture the new `GitHub:` references and update `docs/tasks.md`
4. Continue to Step 5

If all items in scope already have `GitHub:` references, skip Step 4 and continue.

---

## Step 5 — Detect Git State

Run these checks:
1. **Working tree status**: `git status --porcelain` → capture as `WORKING_TREE_STATE`
2. **Upstream tracking**: `git rev-parse --abbrev-ref --symbolic-full-name @{u} 2>/dev/null` → empty if no upstream

### State A: Working tree has uncommitted impl files

This is the normal case. The developer has been running `/implement` and the impl files are still uncommitted.

1. **Cross-reference dirty files vs. newly-completed subtasks**: Match `git status --porcelain` against the `Impl:` and `Test:` paths of the newly-completed subtasks.
2. **If unexpected dirty files exist**: Stop and ask the developer:
   > "Found uncommitted files that don't correspond to any newly-completed subtask:
   > - `path/to/file.ts`
   > Should I (a) include them in the commit, (b) skip them, or (c) stop so you can stash or commit them separately?"
3. **Stage matched files**: `git add` for each `Impl:` file, each `Test:` file, and `docs/tasks.md`.
4. **Commit with a structured message**:
   ```
   {Task IDs} — {Task names}

   Completes:
   - S1.1.1 — Email/password validation logic
   - S1.1.2 — JWT token generation
   - S1.1.3 — Login API endpoint

   Refs: closes #6, closes #7, closes #8

   Managed by /github-create-pr on branch {CURRENT_BRANCH}.
   ```
5. **Push to current branch**:
   - With upstream: `git push`
   - Without upstream: `git push -u origin {CURRENT_BRANCH}`

### State B: Working tree clean, unpushed commits exist

The work is committed locally but not on the remote.
1. Compare local HEAD to remote: `git rev-list --count @{u}..HEAD 2>/dev/null` — if > 0, push.
2. `git push` (or `git push -u origin {CURRENT_BRANCH}` if no upstream)
3. Continue to Step 6

### State C: Working tree clean, everything pushed

Skip directly to Step 6 (PR creation).

### Edge case: Branch creation requested by developer

The skill never creates branches automatically. However, if during the conversation the developer explicitly says "create a branch named X and continue", the skill MAY run `git checkout -b {name}` ONCE and proceed. This requires explicit per-run developer confirmation, not a standing preference.

---

## Step 6 — Create or Update PRs

For each parent task with newly-completed subtasks, check if an open PR already exists for the current branch:
```
gh pr list --head {CURRENT_BRANCH} --state open --json number,title,body
```

### Case A: No open PR exists for this branch

Create a new PR:
```
gh pr create \
  --title "{Task IDs} — {Task Names}" \
  --body "[generated body using PR Body Template]" \
  --label "workflow:agentic" \
  --label "milestone:M1" \
  --label "task:T1.1" \
  --base {DEFAULT_BRANCH} \
  --head {CURRENT_BRANCH}
```

**Important**: Do NOT use `--draft` unless the developer explicitly requests it. Do NOT enable auto-merge. The PR is opened in regular state for human review.

### Case B: An open PR exists for this branch

Update the existing PR:
1. Append the new task and its newly-completed subtasks to the existing "Subtasks Completed" section
2. Update the "Linked Issues" section with new `Closes #N` keywords
3. Update the title to reflect all tasks now covered (e.g., `T1.1, T1.2 — Login Flow & Session Management`)
4. Update labels via `gh pr edit {n} --add-label "task:T1.2"`

```
gh pr edit {n} \
  --title "{updated title}" \
  --body "[regenerated body]"
```

### Case C: A closed/merged PR exists for this branch

This is unusual. Stop and ask the developer:
> "A PR for branch `{CURRENT_BRANCH}` already exists and is {merged/closed}. Opening another PR on the same branch is unusual. Would you like to (a) create a new branch and re-run, or (b) open another PR on this branch anyway?"

Wait for an explicit answer before proceeding.

## Step 7 — Update `docs/tasks.md` with PR References

For the parent task and each newly-completed subtask included in the PR:

**Before:**
```markdown
### T1.1 — Login Flow
- Status: COMPLETE
- GitHub: issue #5

- [x] S1.1.1 — Email/password validation logic
  - Test: `tests/auth/login-validation.test.ts`
  - Impl: `src/auth/validators.ts`
  - GitHub: issue #6
```

**After:**
```markdown
### T1.1 — Login Flow
- Status: COMPLETE
- GitHub: issue #5
- PR: #42

- [x] S1.1.1 — Email/password validation logic
  - Test: `tests/auth/login-validation.test.ts`
  - Impl: `src/auth/validators.ts`
  - GitHub: issue #6
  - PR: #42
```

## Step 8 — Comment on Linked Issues

For each subtask issue and the parent task issue (only if the parent task is fully complete and included in the PR's `Closes #N`), post a comment via:
```
gh issue comment {n} --body "Implementation linked in PR #{pr-number}. This issue will close automatically when PR #{pr-number} merges to {DEFAULT_BRANCH}. Pull requests require human review before merging — no auto-merge is enabled."
```

Do NOT close the issues manually. The `Closes #N` keywords in the PR body handle that on merge.

**Task(s)**: {Task ID — Name}, {Task ID — Name}

## Step 9 — Report

Tell the developer:
1. **PR(s) opened or updated**: Number, title, link
2. **Issues commented on**: List
3. **Git operations**: Commits made, push performed, all on `{CURRENT_BRANCH}`
4. **`docs/tasks.md` updates**: New `PR:` references added
5. **Reminder**: "PRs require human review before merging. The `Closes #N` keywords will auto-close issues on merge — no auto-merge is enabled, so you must approve and merge manually. Open PRs visible at: https://github.com/{owner}/{repo}/pulls?q=is%3Aopen+label%3Aworkflow%3Aagentic"

---

## Error Handling

If `gh` commands fail:
- **Authentication errors**: Tell the developer to run `gh auth login`
- **Rate limit errors**: Stop, report which items succeeded, suggest re-running later
- **Permission errors**: Tell the developer their `gh` token needs `repo` and `pull_request:write` scopes

If git operations fail:
- **Push rejected (non-fast-forward)**: Tell the developer to pull/rebase, do NOT force-push
- **No remote configured**: Recommend running `/github-init` first
- **Detached HEAD**: Tell developer to checkout a named branch
- **Currently on default branch**: Refuse cleanly per Step 1
- **Unexpected dirty files**: Stop and ask the developer (per Step 5 State A)

If PR creation fails:
- **Branch protection blocks the PR**: Report the rule and stop
- **Closes #N references a non-existent issue**: This indicates a bug or a corrupted `docs/tasks.md`. Stop and recommend `/docs-sync`.

If parsing `docs/tasks.md` fails:
- Stop, show the failing line, recommend `/docs-sync`
