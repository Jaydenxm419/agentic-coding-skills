# /github-init — Scaffold GitHub Tracking Board

> **Purpose**: Read `docs/tasks.md` and create the corresponding GitHub milestones, issues, and sub-issues in the remote repository. If no remote is connected, walk the developer through creating one. This is the **static-only** sync — it never commits code, never opens PRs, never touches git. It's safe to run from any branch including the default branch because no code operations occur.
> **Prerequisites**:
>   - `docs/tasks.md` must exist (generated by `/design`)
>   - `gh` (GitHub CLI) must be installed and authenticated
>   - The current directory must be a git repository (with or without a remote — the skill helps create one if needed)
> **Output**: GitHub milestones, issues, and sub-issues + updated `docs/tasks.md` with `GitHub:` references inline
> **Iterative**: Yes — designed to be re-run safely. Existing items are updated; only genuinely new items are created.
> **Position in workflow**: Run after `/design` to scaffold the GitHub tracking board, after `/integrations` if it added new subtasks, or any time `/docs-sync` adds new items. Can also be invoked manually.

---

## Why This Skill Exists

The hierarchical task list in `docs/tasks.md` is the source of truth for project work. This skill mirrors that hierarchy onto GitHub so the team can triage, assign, comment on, and track issues natively. Each issue carries everything a developer (or future agent) needs to act on it: the task description, a summary, an implementation strategy, important reminders, and configuration notes when external services are involved.

Crucially, this skill performs **zero git operations**. It only calls the GitHub REST API via `gh`. That means it works from any branch — including the default branch — and it's the right tool to run on day one of a project, immediately after `/design` sign-off, before any implementation has begun.

If you want to push completed implementation work as a PR, use `/github-create-pr`. If you want a single command that scaffolds AND syncs PRs together, use `/github-sync`.

---

## Instructions for the Agent

You are scaffolding the GitHub tracking board from `docs/tasks.md`. Read `docs/tasks.md`, `docs/architecture.md`, `docs/design.md`, and `docs/integration-registry.md` (if it exists) before starting.

**Behavior rules:**
1. **Verify environment first**: Confirm `gh` CLI is installed and authenticated. If a remote does not exist, walk the developer through creating one before proceeding.
2. **Idempotent operation**: Read the `GitHub:` field on every milestone, task, and subtask in `docs/tasks.md`. Items with a populated `GitHub:` field have already been pushed — UPDATE them. Items without a `GitHub:` field are new — CREATE them.
3. **Status mirror**: For subtasks marked `[x]` in `docs/tasks.md`, the corresponding GitHub issue must be CLOSED. For unchecked subtasks, the issue must be OPEN. Update state on every run.
4. **Hierarchy preservation**: Use GitHub milestones for milestones, issues for tasks, and sub-issues for subtasks. Sub-issues are a native GitHub feature accessed via the REST API.
5. **Title format is non-negotiable**: Every milestone, issue, and sub-issue title MUST start with its task ID. Examples: `M1 — User Authentication`, `T1.1 — Login Flow`, `S1.1.1 — Email/password validation logic`.
6. **Body structure is non-negotiable**: Every issue body must contain the five required sections (Task, Summary, Implementation Strategy, Important Reminders, Configuration Instructions when applicable). See "Issue Body Template" below.
7. **Label everything**: Every issue gets `workflow:agentic` plus its hierarchy labels (`milestone:M1`, `task:T1.1`).
8. **Write back to `docs/tasks.md`**: After each successful GitHub operation, update the corresponding line in `docs/tasks.md` with the GitHub issue number or milestone number.
9. **Never invent task IDs**: Use only the IDs already present in `docs/tasks.md`. If the task list has structural problems, stop and recommend running `/docs-sync` first.
10. **No git operations**: This skill never runs `git add`, `git commit`, `git push`, `git checkout`, or any other git command that modifies state. It only reads the repository identity via `gh repo view`.

## Step 1 — Environment Verification

Run these checks in order. Stop on any failure and tell the developer what to fix.

1. **Check `gh` is installed**: Run `gh --version`. If not found, instruct: "Install GitHub CLI from https://cli.github.com and re-run."
2. **Check `gh` is authenticated**: Run `gh auth status`. If not authenticated, instruct: "Run `gh auth login` and re-run this command."
3. **Check current directory is a git repo**: Run `git rev-parse --is-inside-work-tree`. If not, instruct: "This directory is not a git repository. Run `git init` and re-run."
4. **Check for a GitHub remote**: Run `gh repo view --json nameWithOwner 2>/dev/null`. If this succeeds, capture the `owner/repo` and confirm with the developer:
   > "Detected GitHub repository: `{owner/repo}`. Is this the correct repository to push tasks to?"

If `gh repo view` fails (no remote configured or repo not on GitHub), proceed to Step 1a — Remote Setup Walkthrough.

---

## Step 1a — Remote Setup Walkthrough (only if no remote exists)

If no GitHub remote is connected, walk the developer through creating one. Ask:

1. **"Does a GitHub repository already exist for this project, or do you want me to help you create one?"**
   - If exists: Skip to "Connect existing remote" below
   - If new: Proceed to "Create new repo" below

### Create new repo

Ask:
- **"What should the repository be named?"** (default: directory name, sanitized)
- **"Which GitHub account/organization should own it?"** (default: the authenticated user from `gh auth status`)
- **"Should the repository be public or private?"**
- **"Should I push the current contents of this directory as the initial commit?"**

Then run:
```
gh repo create {owner}/{name} --{public|private} --source=. --remote=origin --push
```

If the working tree has unpushed commits or uncommitted files, confirm with the developer before pushing. **Important**: Even though this skill normally performs no git operations, this initial repo creation is the one exception — and it requires explicit developer confirmation.

### Connect existing remote

Ask:
- **"What's the repository URL or `owner/repo` identifier on GitHub?"**

Then run:
```
git remote add origin {url-or-gh-shorthand}
git fetch origin
```

Verify with `gh repo view --json nameWithOwner` and confirm to the developer.

After remote setup completes, return to Step 2 of the main flow.

## Step 2 — Read & Validate `docs/tasks.md`

1. Read the entire `docs/tasks.md` file
2. Parse the hierarchy: extract every milestone, task, and subtask with their IDs, descriptions, statuses, and existing `GitHub:` references (if any)
3. Validate the structure:
   - Every milestone has an `M{n}` ID
   - Every task has a `T{m}.{n}` ID and belongs to a milestone
   - Every subtask has an `S{m}.{n}.{p}` ID and belongs to a task
   - No orphans (tasks without parent milestones, subtasks without parent tasks)
4. If validation fails, stop and recommend `/docs-sync` to fix the task list first

---

## Step 3 — Set Up Required Labels

Before creating issues, ensure the required labels exist in the repo. Run `gh label list` and check for:

- `workflow:agentic` (color: `5319E7` purple, description: "Issue managed by the agentic-workflow system")
- One label per milestone: `milestone:M1`, `milestone:M2`, etc. (color: `0E8A16` green)
- One label per task: `task:T1.1`, `task:T1.2`, etc. (color: `1D76DB` blue)

For any missing label, create it:
```
gh label create "workflow:agentic" --color "5319E7" --description "Managed by agentic-workflow"
gh label create "milestone:M1" --color "0E8A16" --description "Belongs to milestone M1"
gh label create "task:T1.1" --color "1D76DB" --description "Belongs to task T1.1"
```

## Step 4 — Sync Milestones

For each milestone in `docs/tasks.md`, in order:

### If the milestone has NO `GitHub:` field (new):
1. Create the GitHub milestone:
   ```
   gh api repos/{owner}/{repo}/milestones \
     -f title="M1 — User Authentication" \
     -f description="[milestone description from tasks.md]" \
     -f state="open"
   ```
2. Capture the returned `number` (milestone number)
3. Update `docs/tasks.md` to add the `GitHub:` field:
   ```markdown
   ## M1 — User Authentication
   - Status: NOT STARTED
   - Description: [description]
   - GitHub: milestone #3
   ```

### If the milestone HAS a `GitHub:` field (existing):
1. Update the GitHub milestone if the title or description changed:
   ```
   gh api repos/{owner}/{repo}/milestones/{number} -X PATCH -f title="..." -f description="..."
   ```
2. If the milestone status in `docs/tasks.md` is `COMPLETE`, close the GitHub milestone:
   ```
   gh api repos/{owner}/{repo}/milestones/{number} -X PATCH -f state="closed"
   ```

---

## Step 5 — Sync Tasks (as Issues)

For each task in `docs/tasks.md`:

### If the task has NO `GitHub:` field (new):
1. Generate the issue body using the **Issue Body Template** below
2. Create the GitHub issue:
   ```
   gh issue create \
     --title "T1.1 — Login Flow" \
     --body "[generated body]" \
     --milestone "M1 — User Authentication" \
     --label "workflow:agentic" \
     --label "milestone:M1" \
     --label "task:T1.1"
   ```
3. Capture the returned issue number
4. Update `docs/tasks.md`:
   ```markdown
   ### T1.1 — Login Flow
   - Status: NOT STARTED
   - Requirement refs: [reqs]
   - GitHub: issue #12
   ```

### If the task HAS a `GitHub:` field (existing):
1. Regenerate the issue body using the current state of `docs/tasks.md` and related specs
2. Update the GitHub issue:
   ```
   gh issue edit {number} --body "[new body]" --title "T1.1 — Login Flow"
   ```
3. If the task status is `COMPLETE` AND no PR is currently linked to this task → close the issue. (If a PR is linked, leave the issue open — PR merge will close it.)
4. If the task status was reverted from `COMPLETE` to `IN PROGRESS` → reopen the issue.

---

## Step 6 — Sync Subtasks (as Sub-Issues)

For each subtask under each task:

### If the subtask has NO `GitHub:` field (new):
1. Generate the issue body using the **Issue Body Template**
2. Create the issue:
   ```
   gh issue create \
     --title "S1.1.1 — Email/password validation logic" \
     --body "[generated body]" \
     --milestone "M1 — User Authentication" \
     --label "workflow:agentic" \
     --label "milestone:M1" \
     --label "task:T1.1"
   ```
3. Link it as a sub-issue of the parent task issue via the REST API:
   ```
   gh api -X POST repos/{owner}/{repo}/issues/{parent_number}/sub_issues \
     -f sub_issue_id={child_issue_id}
   ```
   Note: The `sub_issue_id` is the internal database ID, not the issue number. Get it from the issue creation response.
4. If the subtask is `[x]` AND has no `PR:` field AND has no `Impl:` reference → close the issue immediately. Otherwise leave it open. (Subtasks with implementation work get closed via PR merge — that's the responsibility of `/github-create-pr` and `/github-sync`.)
5. Update `docs/tasks.md` to add the `GitHub:` field.

### If the subtask HAS a `GitHub:` field (existing):
1. Regenerate and update the issue body
2. State sync rules:
   - `[x]` AND no `Impl:` reference AND no `PR:` linked → close the issue (no implementation expected)
   - `[x]` AND `Impl:` reference present → leave open. PR merge closes it. If `/github-init` is being run standalone (without a PR present), warn that this subtask has implementation work that should be PR'd.
   - `[ ]` AND issue is closed → reopen the issue

```markdown

**ID**: [M1 / T1.1 / S1.1.1]

**Requirement**: [requirement text from tasks.md]
**Status in tasks.md**: [NOT STARTED / IN PROGRESS / COMPLETE / BLOCKED, or `[ ]` / `[x]` for subtasks]

---

## Summary

[A 2-4 sentence plain-language summary of what this work delivers and why it matters. For milestones, describe the overall capability shipped. For tasks, describe the coherent feature or flow. For subtasks, describe the specific unit of behavior.]
```

## Error Handling

If `gh` commands fail:
- **Authentication errors**: Tell the developer to run `gh auth login`
- **Rate limit errors**: Stop, report which items succeeded, suggest re-running later
- **Permission errors**: Tell the developer their `gh` token needs `repo` scope
- **Sub-issue API errors**: GitHub's sub-issues feature may not be enabled for the repo or org. Fall back to creating a regular issue with a `Parent: #N` line in the body and note this in the report.

If parsing `docs/tasks.md` fails:
- Stop immediately
- Show the developer the specific line that failed to parse
- Recommend running `/docs-sync` to fix structural issues
