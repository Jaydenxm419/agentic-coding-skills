# /implement — Implementation

> **Purpose**: Write production code that passes the existing test suites. Implementation is driven by the spec and validated by tests. The agent checks off subtasks in `docs/tasks.md` as they are completed, linking each to the implementation file. This command treats `docs/tasks.md` as a source of truth — it reads the task list before writing code and writes back to it after tests pass. Before writing any code, the agent runs a **Human Intervention Pre-Flight Check** to surface any non-code setup (account creation, API key generation, webhook configuration, local services, IAM grants, etc.) that must be completed manually before implementation can succeed.
> **Prerequisites**:
>   - `docs/architecture.md`, `docs/design.md`, AND `docs/integration-registry.md` must exist and be signed off (HARD GATE)
>   - `docs/tasks.md` must exist (generated by `/design`)
>   - Test files for the target subtasks must exist (generated by `/test`)
>   - All items in the target task's `Human Setup:` checklist (if any) must be confirmed `[x]` by the developer (HARD GATE — see Step 2)
>   - If any prerequisite is missing, warn and recommend the correct command
> **Output**: Source code files + updated `docs/tasks.md` with completion markers, implementation references, and the persisted Human Setup checklist
> **Iterative**: Yes — run per task. Each invocation implements one task's worth of subtasks.

---

## Instructions for the Agent

You are implementing code from a complete specification. Your code must satisfy existing tests — NOT the other way around. Read `docs/architecture.md`, `docs/design.md`, `docs/integration-registry.md`, and `docs/tasks.md` before writing any code.

**Behavior rules:**
1. **HARD GATE CHECK (planning)**: Before writing any code, verify that `docs/architecture.md`, `docs/design.md`, and `docs/integration-registry.md` exist and contain sign-off timestamps. If any is missing or unsigned, REFUSE to generate code and direct the developer to complete the planning phases.
2. **TASK LIST CHECK**: Read `docs/tasks.md` and identify the target task. Verify that all subtasks in the target task have a `Test:` file path (not `(pending /test)`). If any are missing tests, REFUSE and direct the developer to run `/test` first.
3. **HUMAN INTERVENTION PRE-FLIGHT (HARD GATE)**: Before writing any code, run the Human Intervention Pre-Flight Check (Step 2). Generate a Human Setup Checklist by scanning the Integration Registry, test files, and architecture/design specs. Persist it to `docs/tasks.md` under the target task as a `Human Setup:` field. REFUSE to proceed until every checklist item is marked `[x]` by the developer in the chat. This is a hard stop — no overrides.
4. **INTEGRATION CHECK**: For any subtask with an `Integration:` field, consult `docs/integration-registry.md` for the exact environment variable names, authentication method, and base URL. Use ONLY what the registry defines — never invent new env vars or connection patterns.
5. **Code from spec, validate with tests**: Write code that satisfies the architecture and design specs. Then run the tests to verify. Do NOT modify tests to make them pass.
6. **One task at a time**: Each invocation targets one task (e.g., T1.1). Implement all subtasks within that task.
7. **Check off subtasks**: After each subtask's tests pass, update `docs/tasks.md` to mark it complete and add the implementation file reference.
8. **Rollup statuses**: After all subtasks in a task are complete, update the task status. After all tasks in a milestone are complete, update the milestone status.
9. **Follow clean architecture**: All code must comply with `_standards.md`. The folder structure must match `docs/architecture.md` exactly. External service access must go through the infrastructure layer only.

## Step 1 — Target Selection & Validation

Ask the developer:

> "Which task should I implement? Here is the current state of `docs/tasks.md`:"

Display tasks that are ready for implementation (have tests generated but are not yet complete). Highlight the recommended next task based on dependency order.

### Pre-Implementation Checklist

Before writing any code, verify:

- [ ] `docs/architecture.md` exists and is signed off
- [ ] `docs/design.md` exists and is signed off
- [ ] `docs/integration-registry.md` exists and is signed off
- [ ] `docs/tasks.md` exists
- [ ] Target task has all subtask `Test:` fields populated
- [ ] Any prerequisite tasks (dependencies) are marked COMPLETE
- [ ] The folder structure from `docs/architecture.md` exists (create it if this is the first implementation run)
- [ ] For integration-dependent subtasks: the referenced service exists in the registry

If any check fails, stop and tell the developer what needs to happen first.

Once the planning checklist passes, proceed to Step 2 — the Human Intervention Pre-Flight Check.

## Step 2 — Human Intervention Pre-Flight Check (HARD GATE)

**This is a hard gate. No code is written until this check completes successfully.**

The goal of this step is to surface every non-code prerequisite that the developer must complete manually before implementation can succeed. These are things the agent cannot do for them: creating accounts on external services, generating API keys, configuring webhooks in third-party dashboards, starting local services, granting IAM permissions, etc.

### Step 2a — Scan Three Sources

For the target task, scan the following sources and collect candidate human-setup items:

#### Source 1: Integration Registry
For every subtask in the target task that has an `Integration:` field:
1. Read the matching service entry in `docs/integration-registry.md`
2. Extract every required item that cannot be created by code:
   - **Account existence**: Does this service require an account that may not exist yet?
   - **API keys / secrets**: Are there env vars marked `Required: Yes` that must be obtained from a dashboard?
   - **Webhook setup**: Does the service require registering a webhook endpoint in its dashboard?
   - **OAuth app registration**: Are there client IDs / secrets that come from a developer console?
   - **Redirect URIs**: Must any redirect URIs be added to a service's allowed list?
   - **Domain verification**: Does any service require DNS records or domain ownership verification?
   - **Plan/quota**: Does the integration require a specific paid plan or quota increase?

#### Source 2: Test Files
For every test file referenced by the target task's subtasks:
1. Read the test file
2. Scan for setup requirements:
   - **Env var assertions**: Does the test setup expect specific env vars to be present? Cross-reference these against the Integration Registry — if any are NOT in `.env.example` or not documented, flag as a setup item.
   - **Mock configuration**: Do mocks require fixture data, seed files, or test credentials that must exist on disk?
   - **Local service dependencies**: Does the test require a local database, Redis instance, queue, or other service to be running?
   - **Test database setup**: Are there migrations, seeds, or schema setup steps the developer must run manually?
   - **External test accounts**: Do integration tests require sandbox accounts (e.g., Stripe test mode, OAuth test apps)?

#### Source 3: Architecture & Design Specs
Scan `docs/architecture.md` and `docs/design.md` for any setup tied to the target task's scope:
1. **Infrastructure prerequisites**: Does the architecture call for a specific runtime, database engine, message broker, or cache that must be installed/provisioned?
2. **Deployment targets**: Does the target task depend on a deployment environment being provisioned (e.g., a staging URL that must exist for OAuth callback registration)?
3. **Auth flow prerequisites**: Does an auth flow require pre-configured providers, scopes, or consent screens?
4. **Cross-cutting concerns**: Does logging/monitoring require a pre-existing project ID, DSN, or workspace?
5. **Design-driven config**: Does a design flow assume third-party widgets, payment forms, or external embeds that require account setup?

### Step 2b — Compile the Human Setup Checklist

Deduplicate and group the candidate items by source. For each item, write a concrete, verifiable, action-oriented statement.

**Bad** (vague): `Set up Stripe`
**Good** (concrete): `Create a Stripe account at https://dashboard.stripe.com/register and obtain test-mode keys`

**Bad** (vague): `Start the database`
**Good** (concrete): `Start the local PostgreSQL instance on port 5432 (DATABASE_URL points to localhost:5432 in .env.example)`

Each checklist item must include:
- A short imperative description of the action
- The source that triggered it (Registry / Tests / Architecture)
- Where applicable: a URL, file path, env var name, or service name to make the action unambiguous

### Step 2c — Persist to `docs/tasks.md`

Write the checklist to `docs/tasks.md` under the target task as a `Human Setup:` field. If the field already exists from a prior run, **merge** rather than overwrite — preserve existing `[x]` confirmations for items that haven't changed, add new items as `[ ]`, and remove items that are no longer applicable (note any removals in the chat report).

**Format example:**

```markdown
### T1.2 — OAuth Provider Integration
- Status: NOT STARTED
- Requirement refs: REQ-3, REQ-7
- GitHub: issue #9
- Human Setup:
  - [ ] Create a Google Cloud project and enable the OAuth 2.0 client at https://console.cloud.google.com (Source: Integration Registry — Google OAuth)
  - [ ] Add `http://localhost:3000/auth/callback` and `https://staging.example.com/auth/callback` to the OAuth client's authorized redirect URIs (Source: Integration Registry — Google OAuth)
  - [ ] Copy `GOOGLE_OAUTH_CLIENT_ID` and `GOOGLE_OAUTH_CLIENT_SECRET` from the Google Cloud console into `.env` (Source: Tests — tests/auth/oauth.test.ts expects these env vars)
  - [ ] Start the local Postgres instance on port 5432 (Source: Architecture — Section 2: Data Architecture)

- [ ] S1.2.1 — OAuth redirect flow
  ...
```

### Step 2d — Present & Request Confirmation

Present the checklist to the developer in chat with this exact framing:

> **Human Intervention Required — Hard Stop**
>
> Before I write any code for **{Task ID — Task Name}**, the following non-code setup must be completed by you. I've persisted this checklist to `docs/tasks.md` under the target task.
>
> **From the Integration Registry:**
> - [ ] [item 1]
> - [ ] [item 2]
>
> **From the test files:**
> - [ ] [item 3]
>
> **From the architecture & design specs:**
> - [ ] [item 4]
>
> Please complete each item, then reply confirming which are done. I will mark them `[x]` in `docs/tasks.md`. I cannot proceed to implementation until every item is `[x]`.

### Step 2e — Confirmation Loop

Wait for the developer's response. For each item the developer confirms:
1. Update the checkbox in `docs/tasks.md` from `[ ]` to `[x]`
2. Append a confirmation timestamp inline: `[x] [item] — confirmed YYYY-MM-DD HH:MM`

If the developer reports a blocker on any item (e.g., "I don't have access to the Google Cloud console"), stop and discuss:
- Is there a workaround? (e.g., use a different OAuth provider)
- Should the spec be revisited? (recommend `/integrations` or `/docs-sync`)
- Should this task be deferred and a different one targeted?

Do NOT proceed to Step 3 until every checklist item is `[x]`. This is a hard stop — there are no overrides.

If the developer disputes whether an item is genuinely required, walk through the source that triggered it. If the item is truly spurious, remove it from the checklist (with a brief note in the chat) and continue. If it's a genuine requirement, hold the line.

## Step 3 — Subtask-by-Subtask Implementation

(Formerly Step 2.)

For each subtask in the target task, in order:

1. **Read the subtask** from `docs/tasks.md` — note its description, requirement reference, integration reference (if any), and test file
2. **Read the test file** — understand exactly what behavior is expected
3. **Read the relevant spec sections** — architecture component, design flow, data model
4. **If the subtask has an Integration field**: Read the matching entry in `docs/integration-registry.md`. Use the exact env var names, auth method, and connection pattern documented there. If implementation requires an external dependency NOT in the registry, STOP and warn the developer per `_standards.md` Section 5.
5. **Write the implementation** — create or modify source files as needed
6. **Run the tests** — execute the test file for this subtask
7. **If tests pass**: Proceed to Step 4 (check off)
8. **If tests fail**: Debug, fix the implementation (NOT the tests), and re-run. If the failure reveals a spec ambiguity, flag it and ask the developer for clarification before continuing.
9. **If a test fails because of an environmental issue covered by the Human Setup checklist** (e.g., service not actually running despite being marked `[x]`): Stop. Tell the developer which checklist item appears to be incomplete, and request reconfirmation. Resume only after the developer addresses the environmental issue.

## Step 4 — Check Off Completed Subtask in `docs/tasks.md`

(Formerly Step 3.)

After a subtask's tests pass, update `docs/tasks.md`:

**Before:**
```markdown
- [ ] S1.1.1 — Email/password validation logic
  - Requirement: Users must log in with email and password
  - Test: `tests/auth/login-validation.test.ts`
  - Impl: (pending /implement)
```

**After:**
```markdown
- [x] S1.1.1 — Email/password validation logic
  - Requirement: Users must log in with email and password
  - Test: `tests/auth/login-validation.test.ts`
  - Impl: `src/auth/validators.ts`
```

### What to record in the Impl field:
- The **primary file** where the subtask's logic lives
- If the implementation spans multiple files, list the main entry point file
- Use the path relative to the project root

## Step 5 — Rollup Status Updates

(Formerly Step 4.)

After all subtasks in the target task are checked off:

1. **Update the task status** from `NOT STARTED` or `IN PROGRESS` to `COMPLETE`
2. **Check the parent milestone**: If all tasks in the milestone are now COMPLETE, update the milestone status to `COMPLETE`
3. **Update the Summary table** at the top of `docs/tasks.md` (increment Completed count, decrement Remaining count)

### Status Rules (strict rollup from `_standards.md` Section 6):

| Condition | Status |
|-----------|--------|
| Zero subtasks complete | NOT STARTED |
| At least one subtask complete, not all | IN PROGRESS |
| All subtasks complete with Impl references | COMPLETE |
| A subtask cannot proceed (external dependency) | BLOCKED — describe blocker |

A task CANNOT be marked COMPLETE unless every subtask has: `[x]` checkbox, a `Test:` file path (not pending), and an `Impl:` file path (not pending).

The `Human Setup:` checklist is preserved on the completed task as a historical record of the manual setup that was required. Do NOT delete it after the task is COMPLETE — future audits and re-runs reference it.

## Step 6 — Implementation Report

(Formerly Step 5.)

After completing the target task, tell the developer:

1. **Human Setup confirmed**: List the checklist items that were confirmed before implementation began
2. **Subtasks completed**: List each subtask ID, description, and implementation file
3. **Tests passing**: Confirm all tests pass for the completed task
4. **Integration references**: List any external services used and confirm they matched the registry
5. **Task status**: The current status of the task and its parent milestone
6. **Spec gaps found** (if any): List any ambiguities discovered during implementation
7. **Next recommended task**: Based on `docs/tasks.md`, suggest the next task to implement
8. **Overall progress**: "X of Y subtasks complete across the project (Z%)"
9. **GitHub PR** (if `GitHub:` references exist in `docs/tasks.md`): Note that the completed work is ready to be PR'd. Recommend running `/github-create-pr` to open a Pull Request for the just-completed task. The next `/github-create-pr` run will:
   - Detect the newly-checked-off subtasks (now `[x]` with `Impl:` references but no `PR:` field)
   - Group them under the parent task (e.g., T1.1)
   - Operate strictly on the current branch — commit dirty files there and push (never switching branches)
   - Open ONE PR for the parent task with `Closes #N` keywords for every linked issue
   - Comment on each issue linking the PR
   - On PR merge (which a human reviewer must perform — never automated), GitHub auto-closes the issues
   **Important**: Make sure the current branch is a feature branch (not `main`/`master`) before running `/github-create-pr`. The skill will refuse to commit or open a PR if you are currently on the repository's default branch.
   This is optional but recommended if the team uses GitHub Issues and PRs for tracking.

## Implementation Standards

All code must comply with `_standards.md`:

- **Clean architecture**: Dependencies point inward. Domain has no external imports. External services accessed only through infrastructure layer.
- **Integration registry compliance**: Use only documented env var names, auth methods, and connection patterns. Never invent new ones.
- **Human setup compliance**: Never bypass the Step 2 hard gate. If implementation reveals a missed setup item mid-task, stop, add it to the `Human Setup:` checklist, and request confirmation before continuing.
- **Error handling**: No silent failures. Typed errors. Boundary error handling. Graceful degradation for external service failures.
- **Naming**: Follow the conventions for the project's language.
- **Documentation**: Public APIs and complex logic must have inline documentation.
- **No test modification**: If a test seems wrong, flag it — do not change it. The test was derived from the spec. If the spec is wrong, that's a design issue to resolve with the developer.
