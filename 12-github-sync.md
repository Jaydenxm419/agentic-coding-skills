# /github-sync — Full Reconciliation Between `docs/tasks.md` and GitHub

> **Purpose**: A long-running reconciliation skill that ensures the entire local task list in `docs/tasks.md` is fully reflected on GitHub. For every milestone/task/subtask, verify a corresponding GitHub item exists. For every completed task (with all subtasks `[x]` and implementation files referenced), verify a sibling or parent PR exists. When something is missing, delegate to `/github-init` (for missing milestones, issues, or sub-issues) or `/github-create-pr` (for missing PRs). This is the periodic full-sweep — not the every-implementation tool.
> **Prerequisites**:
>   - `docs/tasks.md` must exist (generated by `/design`)
>   - `gh` (GitHub CLI) must be installed and authenticated
>   - The current directory must be a git repository connected to a GitHub remote
> **Output**: Reconciliation report + any GitHub items created via `/github-init` + any PRs opened via `/github-create-pr` + updated `docs/tasks.md`
> **Iterative**: Yes — designed for periodic runs (e.g., after a sprint of work, before a release, after `/docs-sync` adds new items)
> **Position in workflow**: Run periodically to catch drift between `docs/tasks.md` and GitHub. Especially useful after batch implementation work, after `/docs-sync` adjustments, or before a release.

---

## Why This Skill Exists

`/github-init` scaffolds the GitHub tracking board. `/github-create-pr` opens PRs for newly-completed work. Both are focused, single-purpose skills.

But over time, drift accumulates: subtasks get added by `/docs-sync` and never pushed; PRs that were supposed to close issues got closed without merging; the developer ran `/implement` and forgot to follow up with `/github-create-pr`. This skill is the periodic full reconciliation — a longer-running sweep that walks the entire `docs/tasks.md` hierarchy, identifies every gap, and delegates to the focused skills to close those gaps.

It's the right tool for: end-of-sprint cleanup, pre-release verification, post-`/docs-sync` reconciliation, or any time you want to ensure GitHub fully mirrors your local plan.

---

## Instructions for the Agent

You are reconciling the local task list with the GitHub state. Read `docs/tasks.md`, `docs/architecture.md`, `docs/design.md`, and `docs/integration-registry.md` (if it exists) before starting.

**Behavior rules:**
1. **Verify environment first**: Same checks as `/github-init` Step 1.
2. **Branch-aware**: Like `/github-create-pr`, this skill refuses PR creation when the current branch is the repository's default branch. However, the issue/milestone scaffolding portion can run from any branch (because no git operations are involved).
3. **No auto-merging**: Like `/github-create-pr`, this skill never merges PRs.
4. **Delegate, don't duplicate**: When a milestone/task/subtask is missing from GitHub, delegate to `/github-init`'s logic. When a PR is missing for a completed task, delegate to `/github-create-pr`'s logic. The skill itself is a reconciliation orchestrator — the actual creation work happens in the other skills' procedures.
5. **Report before acting**: First, do a full read-only pass and report ALL gaps to the developer. Then ask which gaps to close before performing any creation. This is a long-running skill — the developer should know what they're committing to.
6. **Show progress**: For long runs (many gaps), report progress as items are created.

## Step 1 — Environment Verification

Run the same checks as `/github-init` Step 1:
1. `gh --version`
2. `gh auth status`
3. `git rev-parse --is-inside-work-tree`
4. `gh repo view --json nameWithOwner` — capture `OWNER/REPO`. If no remote, recommend running `/github-init` first to walk through remote setup, then re-run.

Capture:
- `DEFAULT_BRANCH` via `gh repo view --json defaultBranchRef -q .defaultBranchRef.name`
- `CURRENT_BRANCH` via `git branch --show-current`

---

## Step 2 — Read & Validate `docs/tasks.md`

Same as `/github-init` Step 2. If validation fails, stop and recommend `/docs-sync`.

---

## Step 3 — Build the Reconciliation Map

Walk the entire `docs/tasks.md` hierarchy and build a map of every item with its current state and target state:

For every milestone:
- **Local state**: ID, name, description, status, `GitHub:` ref (if any)
- **Remote state**: query `gh api repos/{OWNER}/{REPO}/milestones?state=all` and match by title prefix or by the captured `GitHub:` number
- **Gap detected**: Missing from remote? Title/description out of sync? Status mismatch?

For every task:
- **Local state**: ID, name, status, `GitHub:` ref, `PR:` ref
- **Remote state**: `gh issue view {n}` if `GitHub:` ref exists; `gh issue list --label task:T1.1 --json number,title,state` otherwise
- **Gap detected**: Missing issue? Out-of-sync body? Should have a PR linked but doesn't?

For every subtask:
- **Local state**: ID, name, `[x]` or `[ ]`, `Test:`, `Impl:`, `GitHub:` ref, `PR:` ref
- **Remote state**: `gh issue view {n}` if `GitHub:` ref exists
- **Gap detected**: Missing issue? Issue not linked as sub-issue? `[x]` with `Impl:` but no `PR:` reference (orphaned completed work)?

For every PR currently linked from `docs/tasks.md`:
- **Remote state**: `gh pr view {n} --json state,mergedAt,headRefName,baseRefName`
- **Gap detected**: PR closed without merging but task is still `[x]` (work needs re-PR)? PR open with stale title/body? PR's head branch was deleted?

For every open PR labeled `workflow:agentic` in the repo:
- **Local state**: Look up via the PR title prefix (e.g., `T1.1`) and find the matching task in `docs/tasks.md`
- **Gap detected**: PR exists but no corresponding task in `docs/tasks.md` (manual edit)? Task in `docs/tasks.md` doesn't reference this PR?

---

## Step 4 — Categorize and Present Gaps

Organize the gaps by category. For each category, list the affected items.

```markdown
## Reconciliation Plan

### Category 1: GitHub items missing for local tasks
The following items exist in `docs/tasks.md` but have no corresponding GitHub item:

- M2 — Dashboard (no `GitHub:` reference, no remote milestone matches)
- T2.1 — Dashboard layout (no GitHub issue)
- S2.1.1, S2.1.2, S2.1.3 — Dashboard subtasks (no GitHub sub-issues)

**Resolution**: Invoke /github-init logic to create them.

### Category 2: GitHub items out of sync
Items where the remote state differs from `docs/tasks.md`:

- T1.1 — Title was changed locally but not on GitHub
- M1 — Milestone description updated locally; remote is stale

**Resolution**: Invoke /github-init logic to update bodies and statuses.

### Category 3: Completed work not yet PR'd
Subtasks marked `[x]` with `Impl:` references but no PR linked:

- T1.1 (Login Flow) → S1.1.1, S1.1.2, S1.1.3 — completed but no PR exists
- T2.3 (Settings page) → S2.3.1 — completed but no PR exists

**Resolution**: Invoke /github-create-pr logic to open PRs. Will require switching to a feature branch for tasks where work is on the default branch.

### Category 4: Stale PRs
PRs that no longer reflect the current task state:

- PR #42 (T1.1) — closed without merging, but task is still `[x]` in tasks.md
- PR #51 (T1.4) — open, but title says "T1.4" while the task in tasks.md was renamed

**Resolution**: Update the PR body or comment on the PR for review.

### Category 5: Orphan PRs
Open `workflow:agentic` PRs without a matching task in `docs/tasks.md`:

- PR #67 (titled "T9.9") — no T9.9 in `docs/tasks.md`. May indicate a manual PR edit or a deleted task.

**Resolution**: Flag for human review. Skill takes no automatic action.

### Category 6: State mismatches
Subtasks where `[x]/[ ]` doesn't match the issue state:

- S1.2.1 — local `[ ]`, remote issue is closed
- S2.4.5 — local `[x]`, remote issue is open (may be expected if PR is pending)

**Resolution**: Re-sync via /github-init logic.
```

Present this plan to the developer and ask:
> "Which categories should I reconcile? Pick one of:
> - **All** — work through every gap in order
> - **Specific categories** — e.g., 'Categories 1, 3, 4'
> - **Dry run only** — show the plan without making any changes
> - **None** — exit"

Wait for an explicit answer before proceeding.

---

## Step 5 — Reconcile (Delegated)

Based on the developer's selection, work through each chosen category. For each category, follow the appropriate sub-skill's logic:

### Category 1 (Missing GitHub items)
Invoke `/github-init`'s Steps 3-6 logic, scoped to the gap items. Show progress as each item is created. Update `docs/tasks.md` with new `GitHub:` references.

### Category 2 (Out-of-sync items)
Invoke `/github-init`'s "existing item" branches in Steps 4-6. For each item, regenerate the body from current spec content and update via `gh api`/`gh issue edit`.

### Category 3 (Missing PRs)
**Branch check first**: If the current branch is the default branch, REFUSE this category and tell the developer to switch to a feature branch and re-run. Categories 1, 2, 4, 5, 6 can still proceed (they don't require git operations).

If on a feature branch, invoke `/github-create-pr`'s Steps 5-8 logic for each parent task with completed-but-unpublished subtasks. The skill stays on the current branch — it does NOT switch branches between tasks. If multiple parent tasks have work on different feature branches (which would be unusual), only PR the ones on the current branch and flag the others as "pending — switch to branch X and re-run."

### Category 4 (Stale PRs)
For each stale PR:
- If the PR was closed-without-merging but the task is still `[x]` → comment on the PR: "This PR was closed without merging, but the task is still marked complete in `docs/tasks.md`. To re-publish this work, switch to a new feature branch and run `/github-create-pr`."
- If the PR is open but title/body is stale → update via `gh pr edit`

### Category 5 (Orphan PRs)
Flag and report. The skill never closes a PR that lacks a local counterpart — that's a human decision. Output the list and recommend the developer review them manually.

### Category 6 (State mismatches)
For each mismatch, apply the local-as-truth rule:
- `[x]` locally, open remotely, no PR linked → close the remote issue (call `gh issue close {n}` with comment "Closed by /github-sync — task marked complete in `docs/tasks.md`")
- `[x]` locally, open remotely, PR linked → leave open (PR merge will close it). Note in report.
- `[ ]` locally, closed remotely → reopen via `gh issue reopen {n}` with comment "Reopened by /github-sync — task no longer marked complete in `docs/tasks.md`"

## Error Handling

Inherit error handling from `/github-init` and `/github-create-pr`. Additionally:

- **Long-running rate limits**: Because this skill may make many `gh` API calls in a single run, watch for rate limit responses (HTTP 403 with rate-limit headers). If hit, stop, report progress, and tell the developer to re-run after the limit resets.
- **Mid-run interruption**: If the developer cancels mid-run, the skill should leave `docs/tasks.md` in a consistent state — never leave half-updated references. Save state as you go (one item at a time) so a re-run resumes cleanly.
- **Conflicting categories**: If the developer asks for Category 3 (PR creation) while on the default branch, refuse Category 3 specifically and proceed with the others. Don't refuse the whole run.
