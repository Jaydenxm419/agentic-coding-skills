# /test — Test Suite Generation (Test-First)

> **Purpose**: Generate test suites from the project spec for a specific milestone, task, or set of subtasks. Tests are written BEFORE implementation — this is the test-first mandate. The tests define the contract that `/implement` must satisfy.
> **Prerequisites**:
>   - `docs/architecture.md`, `docs/design.md`, AND `docs/integration-registry.md` must exist and be signed off (HARD GATE)
>   - `docs/tasks.md` must exist (generated by `/design`)
>   - If any prerequisite is missing, warn and recommend the correct command
> **Output**: Test files in the project's test directory + updated `docs/tasks.md` with test file references
> **Iterative**: Yes — run per task or milestone.

---

## Instructions for the Agent

You are generating tests from the specification. These tests define the behavior that the implementation must satisfy. Read `docs/architecture.md`, `docs/design.md`, `docs/integration-registry.md`, and `docs/tasks.md` before writing any tests.

**Behavior rules:**
1. **HARD GATE CHECK**: Verify that `docs/architecture.md`, `docs/design.md`, and `docs/integration-registry.md` exist and contain sign-off timestamps. If any is missing or unsigned, REFUSE to generate tests and direct the developer to complete the planning phases.
2. Ask the developer which milestone or task to target. Reference `docs/tasks.md` by ID (e.g., "M1", "T1.2", "S1.2.3").
3. Tests must be derived from the spec — not invented. Every test must trace to a subtask in `docs/tasks.md` and a requirement in `docs/requirements.md`.
4. For subtasks with an `Integration:` field, consult `docs/integration-registry.md` for the service details. Test configuration MUST include mock/stub values for every required environment variable. Integration tests must mock the external service based on the registry's documented behavior.
5. Tests must follow the standards in `_standards.md` (naming, isolation, edge cases).
6. After generating tests, update `docs/tasks.md` to fill in the `Test:` field for each covered subtask.
7. All generated tests should FAIL at this point — there is no implementation yet. This is correct and expected.

---

## Step 1 — Target Selection

Ask the developer:

> "Which part of the project should I generate tests for? Here are the available items from `docs/tasks.md`:"

Display the current milestone/task list with statuses. Let the developer pick by ID.

If the developer picks a milestone, generate tests for all tasks within it. If they pick a task, generate tests for all subtasks within it.

---

## Step 2 — Spec Analysis

For each subtask in the target scope:

1. Read the subtask description and its requirement reference
2. Find the corresponding architecture section (data model, API contract, component boundary)
3. Find the corresponding design section (screen spec, interaction flow, state management)
4. If the subtask has an `Integration:` field, read the matching service entry from `docs/integration-registry.md`
5. Identify the testable behaviors:
   - **Happy path**: The expected behavior when inputs are valid
   - **Validation / rejection**: What happens with invalid inputs
   - **Edge cases**: Boundary conditions, empty states, concurrent operations
   - **Error handling**: External failures, timeouts, unexpected data
   - **Integration mocking**: For external services, test with mocked responses based on registry docs

---

## Step 3 — Test Generation

For each subtask, generate:

1. **Unit tests**: Test the isolated logic (domain layer, utility functions, validators)
2. **Integration tests**: Test the interaction between components (API endpoint + database, UI + state management). For external services, use mocks/stubs configured from the Integration Registry.
3. **Edge case tests**: At least one boundary condition per subtask

Follow the test naming convention from `_standards.md`.

---

## Step 4 — Update `docs/tasks.md`

After generating tests, update `docs/tasks.md` to reflect the test file paths:

**Before:**
```markdown
- [ ] S1.1.1 — Email/password validation logic
  - Requirement: Users must log in with email and password
  - Test: (pending /test)
  - Impl: (pending /implement)
```

**After:**
```markdown
- [ ] S1.1.1 — Email/password validation logic
  - Requirement: Users must log in with email and password
  - Test: `tests/auth/login-validation.test.ts`
  - Impl: (pending /implement)
```

Do NOT change the checkbox status. Tests being written does not mean the subtask is complete — implementation must also pass.

---

## Step 5 — Confirm & Guide

After tests are written, tell the developer:

1. **Summary**: How many tests were generated (unit, integration, edge case breakdown)
2. **Coverage map**: Which subtasks are now covered by tests (by ID)
3. **Expected state**: "All tests should currently FAIL because no implementation exists yet. This is correct."
4. **Integration mocks**: List which external services were mocked and which env vars the test config expects
5. **Next step**: "Run `/implement` targeting the same task or milestone. The implementation is complete when all these tests pass."
6. **Gaps found** (if any): List any spec ambiguities discovered during test writing
