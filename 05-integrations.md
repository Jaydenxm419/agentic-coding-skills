# /integrations — External Services & Environment Configuration Registry

> **Purpose**: Map every external service, third-party API, database provider, VPS connection, analytics tool, and environment variable the project depends on — BEFORE any code is written. This stage produces a single Integration Registry document that becomes the authoritative source of truth for all external connections and configuration. It also validates and may extend `docs/tasks.md` with integration-specific subtasks.
> **Prerequisites**: `docs/design.md` must exist and be signed off. `docs/tasks.md` must exist (generated by `/design`). If missing or unsigned, warn and recommend running `/design` first.
> **Output**: `docs/integration-registry.md` + potential updates to `docs/tasks.md`
> **Iterative**: Yes — loops through integration discovery and environment mapping until all external dependencies are cataloged and the developer signs off.
> **Position in workflow**: This is the LAST planning stage. After sign-off here, the hard gate opens and implementation begins.

---

## Why This Stage Exists

When an agentic coding assistant implements features, it frequently encounters environment variables, API keys, database connection strings, and external service URLs mid-task. Without a pre-established map of these dependencies, configuration gets created ad-hoc — scattered across files, inconsistently named, and difficult to trace after the fact.

This stage solves that by requiring every external dependency to be:
1. **Identified** — What is it and why does the project need it?
2. **Documented** — How does the application connect to it?
3. **Named** — What environment variable(s) does it require?
4. **Scoped** — Which environments need it and what values differ?
5. **Linked to tasks** — Which subtasks in `docs/tasks.md` depend on this integration?

The resulting Integration Registry is referenced by `/test`, `/implement`, and `/docs-sync` to ensure configuration is never invented on the fly.

## Instructions for the Agent

You are creating the Integration Registry for the project. Read `docs/project-init.md`, `docs/requirements.md`, `docs/architecture.md`, `docs/design.md`, and `docs/tasks.md` before starting.

**Behavior rules:**
1. Walk through integration discovery one category at a time. Do NOT dump all questions at once.
2. After each category, summarize what you understood and ask for corrections.
3. Cross-reference the architecture spec — every external dependency mentioned in `docs/architecture.md` MUST appear in this registry. Flag any that are missing.
4. Cross-reference the requirements spec — any requirement that implies an external service must have a corresponding registry entry.
5. Cross-reference the task list — every subtask in `docs/tasks.md` flagged with an `Integration:` field must have a matching registry entry.
6. Every environment variable MUST follow the naming convention defined in this document.
7. No integration is complete until it has: a service name, a purpose, an auth method, all required env vars, and at least one endpoint or connection string.

## Phase 1 — Environment Strategy

Before cataloging integrations, establish the environment landscape for this project.

Ask the developer:

1. **How many environments will this project have?** Provide these options and let them choose:
   - Local development only
   - Local + Production
   - Local + Staging + Production
   - Local + Development + Staging + Production
   - Custom (describe)

2. **How will environment variables be managed?**
   - `.env` files (with `.env.example` committed to repo)
   - Platform-provided (Vercel, Railway, Heroku, etc.)
   - Secret manager (AWS Secrets Manager, Vault, Doppler, etc.)
   - Combination (describe)

3. **Is there an existing `.env` file or configuration from a previous project to carry over?** If yes, ask the developer to share it or list the variables.

Record the answers. These determine the structure of the Environment Variable Map in Phase 5.

## Phase 2 — Integration Discovery

Walk through each category below. For EACH category, ask the developer if the project uses any services in that category. If yes, collect the details specified. If no, confirm and move on.

### Category 1: Databases & Data Stores

Ask: "Does this project connect to any databases, caches, object storage, or file storage services?"

For each service identified, collect:
- **Service name** (e.g., PostgreSQL on Supabase, Redis on Upstash, S3 on AWS)
- **Purpose** — What data does it store and which components access it?
- **Connection method** — Direct connection string, ORM, SDK, REST API?
- **Authentication** — Connection string with credentials, API key, IAM role, service account?
- **Required environment variables** — List every variable needed (URL, host, port, username, password, database name, etc.)
- **Environment differences** — Does the connection string differ per environment? Is there a local dev instance?

### Category 2: Authentication & Identity Providers

Ask: "Does this project use any external authentication services?"

Examples to prompt: OAuth providers (Google, GitHub, Apple), auth platforms (Auth0, Clerk, Supabase Auth, Firebase Auth), SSO/SAML providers.

For each, collect:
- **Service name**
- **Auth flow** — OAuth 2.0, OIDC, API key, JWT verification, SAML?
- **Required environment variables** — Client ID, client secret, redirect URIs, issuer URL, etc.
- **Callback/redirect URLs per environment**
- **Scopes or permissions requested**

### Category 3: Third-Party APIs

Ask: "Does this project consume any external APIs that are not databases or auth providers?"

Examples to prompt: Payment processors (Stripe, PayPal), email services (SendGrid, Resend, Postmark), SMS (Twilio), maps (Google Maps, Mapbox), AI/ML (OpenAI, Anthropic), search (Algolia), CMS (Contentful, Sanity).

For each, collect:
- **Service name**
- **Purpose** — What feature depends on this API?
- **Base URL** — Does it differ per environment (sandbox vs production)?
- **Authentication** — API key, OAuth token, bearer token, webhook secret?
- **Required environment variables**
- **Rate limits or quotas** — Are there known limits that affect implementation?
- **Webhook configuration** — Does this service send webhooks to the application? If so, what endpoint receives them and is there a webhook signing secret?

### Category 4: Hosting & Infrastructure

Ask: "Where is this project deployed and does it connect to any infrastructure services?"

Examples to prompt: VPS providers (DigitalOcean, Linode, Hetzner), PaaS (Vercel, Railway, Fly.io, Render), cloud services (AWS, GCP, Azure), CDN (Cloudflare, Fastly), container registries.

For each, collect:
- **Service name**
- **Purpose** — Hosting, CDN, DNS, container registry, etc.
- **Connection method** — CLI, API, dashboard-only?
- **Required environment variables** — API tokens, project IDs, region, etc.
- **Deploy-specific variables** — Build commands, output directories, environment-specific URLs

### Category 5: Monitoring, Analytics & Observability

Ask: "Does this project use any monitoring, analytics, error tracking, or logging services?"

Examples to prompt: Error tracking (Sentry, Bugsnag), analytics (PostHog, Mixpanel, Google Analytics), logging (Datadog, LogRocket), uptime (Better Uptime, Pingdom), performance (Vercel Analytics, Lighthouse CI).

For each, collect:
- **Service name**
- **Purpose** — Error tracking, user analytics, performance monitoring, logging?
- **Integration method** — SDK, script tag, API, sidecar?
- **Required environment variables** — DSN, project key, API key, measurement ID?
- **Environment behavior** — Should it be active in all environments or production-only?

### Category 6: Communication & Notifications

Ask: "Does this project send or receive any communications — email, SMS, push notifications, in-app messages, or webhooks to external systems?"

For each, collect:
- **Service name**
- **Purpose** — Transactional email, marketing email, SMS alerts, push notifications?
- **Required environment variables**
- **Sender identity** — Verified domain, sender email, phone number?
- **Template system** — Does the service host templates or are they in-code?

### Category 7: Other External Services

Ask: "Are there any other external services, tools, or connections that haven't been covered? This includes things like: feature flag services, A/B testing tools, CRM integrations, background job processors, scheduled task services, PDF generation, image processing, geolocation, or any custom internal APIs."

For each, collect the same detail pattern: name, purpose, connection method, auth, env vars, environment differences.

## Phase 3 — Environment Variable Naming Convention

Before finalizing the registry, establish and confirm the naming convention with the developer.

**Proposed default convention:**

```
[SERVICE]_[DETAIL]

Examples:
  DATABASE_URL
  DATABASE_HOST
  STRIPE_SECRET_KEY
  STRIPE_PUBLISHABLE_KEY
  STRIPE_WEBHOOK_SECRET
  SUPABASE_URL
  SUPABASE_ANON_KEY
  SENTRY_DSN
  NEXT_PUBLIC_*          (for client-exposed variables in Next.js)
  VITE_*                 (for client-exposed variables in Vite)
```

**Rules:**
- ALL_CAPS with underscores
- Service name prefix groups related variables together
- No abbreviations unless universally understood (URL, API, DSN, etc.)
- Framework-specific prefixes for client-exposed variables (NEXT_PUBLIC_, VITE_, REACT_APP_, etc.)
- Secret values are NEVER committed to the repository
- `.env.example` contains every variable key with placeholder values or descriptions — NEVER real credentials

Ask the developer:
- "Does this naming convention work for you, or do you have a preferred pattern?"
- "Does your framework require a specific prefix for client-exposed variables?"

## Phase 4 — Cross-Reference Validation

Before generating the registry, perform these automated checks:

### Architecture Cross-Reference
Scan `docs/architecture.md` for any component that depends on an external service, any API contract referencing an external endpoint, any data entity stored externally, any mention of environment variables or configuration.

**Flag any external dependency found in the architecture spec that is NOT in the integration registry.**

### Requirements Cross-Reference
Scan `docs/requirements.md` for requirements that imply external services (keywords: "send", "notify", "pay", "store files", "upload", "authenticate with", "track", "monitor", "analyze") and any named third-party service.

**Flag any implied integration found in requirements that is NOT in the integration registry.**

### Design Cross-Reference
Scan `docs/design.md` for UI flows that depend on external data (e.g., "display map", "show payment form", "social login button") and state management that references external data sources.

**Flag any design dependency that is NOT in the integration registry.**

### Task List Cross-Reference
Scan `docs/tasks.md` for every subtask with an `Integration:` field. Verify each references an integration that now exists in the registry.

**Flag any subtask integration reference that has no matching registry entry.**

Present all flags to the developer and resolve them before proceeding.

## Phase 5 — Task List Update

After the registry is complete, review `docs/tasks.md` for any new subtasks that need to be added:

1. **Integration setup subtasks**: If an external service requires initial setup code (e.g., SDK initialization, config module, middleware), and no existing subtask covers this, add new subtasks to the appropriate task.
2. **Environment validation subtasks**: If the project needs a startup validation step that checks for required env vars, add a subtask for it.
3. **New integration subtasks**: If any integration was discovered during this phase that was not anticipated during `/design`, add corresponding subtasks.

When adding new subtasks to `docs/tasks.md`:
- Follow the existing ID numbering scheme (append to the appropriate milestone/task)
- Set status to `NOT STARTED`
- Set Test and Impl fields to `(pending /test)` and `(pending /implement)`
- Add the `Integration:` field referencing the registry entry
- Update the Summary table counts

Tell the developer what was added and why.

## How Other Commands Use This Registry

### `/test`
- Must verify that test configuration includes mock/stub values for every required environment variable in the registry
- Integration tests must reference the registry for expected service behavior

### `/implement`
- Before writing any module that touches an external service, the agent MUST consult the Integration Registry for the correct environment variable names, authentication method, and base URL pattern
- If implementation discovers a NEW external dependency not in the registry, the agent MUST stop, warn, and recommend running `/integrations` to update

### `/docs-sync`
- Must compare `.env.example` against the Integration Registry and flag discrepancies
- Must check that no environment variable exists in code that is not in the registry

### `/audit`
- Must include an "Integration Health" section that verifies: all registry entries are still used, no undocumented env vars exist, `.env.example` is in sync, no secrets are hardcoded
